## Воспроизводимый набор

`benchmarks/multilingual-v1.json`: 18 чатов, ровно 6 RU / 6 KZ / 6 EN. 17 исходных синтетических DEV фиксируются только ID и SHA-256, без публикации приватных транскриптов. Один собственный KZ кейс с переключением RU/KZ явно помечен `team_synthetic`, имеет ID `cqa-synthetic-kz-codeswitch-v1` и хранится в отдельном dataset `BENCHMARK`. Его текст в `benchmarks/team_synthetic.json` не является данными организаторов и не попадает в DEV/PROD.

Покрытие: исходный контекст бота, N/A, вежливое корректное обслуживание, подтверждение личности до действия, пропуск идентификации, разглашение, оскорбление, платное предложение в обход компании, спорная/частичная консультация, плохое завершение, неполный запрос и обрыв. Теги покрытия — указатели сценариев, не значения Ground Truth. Они не отправляются моделям.

Есть замороженные calibration/holdout: по 3 RU/KZ/EN в каждом, всего 9+9. Preflight использует только calibration. После появления независимых эталонов изменения prompt сравниваются на calibration; holdout не используется для подбора правил. Нужна новая версия pipeline, а при смене входов/чек-листа — новый manifest, а не правка исходных DEV.

## Независимая человеческая разметка

В UI → Benchmark → «Загрузить» → случай → «Независимый A» или «Независимый B». Отображаются исходный транскрипт, официальный чек-лист и только собственная ранее сохранённая разметка выбранного раунда. Значения из AI не подставляются. Пустое поле означает «не размечено», а `null` означает только явно выбранное N/A с объяснением.

Для каждого из восьми критериев человек выбирает допустимое значение, rationale и номера исходных реплик; N/A требует na_reason. A/B должны иметь разные имена экспертов. Все версии неизменяемы. UI без авторизации не может удостоверить реальную личность или гарантировать, что человек не смотрел сторонние ответы; команда отвечает за независимость проверяющих.

После обоих раундов «Согласование» показывает человеческие A/B и отчёт о расхождениях значений/evidence. Итоговая версия требует явного решения человека, причины и точных `based_on=[latest_A_id,latest_B_id]`. Даже одинаковые A/B не становятся консенсусом автоматически. Изменение любого раунда делает старый итог неприменимым до нового согласования. Другой текст/чек-лист/manifest также меняет контекст разметки.

Без действующего консенсуса статус `unlabeled`, accuracy — `null`/«—», не 0 и не придуманные проценты. Статус частичной разметки и знаменатели показываются явно.

Формат одной записи:

```json
{
  "conversation_id": "исходный-ID",
  "slot": "A",
  "reviewer": "Имя независимого эксперта",
  "origin": "human",
  "criteria": [],
  "based_on": [],
  "decision_reason": ""
}
```

`criteria` необходимо вручную заполнить всеми 8 допустимыми Assessment; пустой массив не принимается. Поля каждого: `criterion_id`, `value`, `rationale`, `evidence_turns`, при N/A — `na_reason`; optional `evidence_quotes=[{turn,quote}]` проверяются на точное совпадение. JSON-импорт массива атомарен: ошибка не оставляет половину набора.

Пустые шаблоны A/B/consensus содержат **UNLABELED**, намеренно невалидное значение, пока его не выберет эксперт. Они не являются Ground Truth.

## Метрики и корректность сравнения

Сравниваются только пары двух точных model_id на идентичных хешах входов, Official v1 и одной общей версии pipeline/параметров. Хеш pipeline включает system/fact prompts, JSON Schema, код движка/адаптеров и параметры. Последние несопоставимые версии не подменяют парные результаты; в отчёте одна общая версия эксперимента, а не смесь лучших prompt для разных чатов. Через `?pipeline_sha256=...` можно выбрать историческую общую версию.

Старый RU smoke не включается автоматически: он не содержит нового полного контекста эксперимента. Апелляционные ревизии, Mock и одиночные модельные оценки исключены из accuracy. Их совпадение не используется как эталон.

Отчёт содержит:

- Micro exact-match по значениям восьми критериев; полное совпадение всех восьми на диалоге — отдельная метрика. `final_score` вообще не читается при расчёте accuracy.
- Срезы RU/KZ/EN, каждого criterion_id и calibration/holdout. Отсутствие меток в срезе даёт `null`, не ноль.
- Матрицы N/A: true N/A / predicted N/A, true N/A / predicted applicable, true applicable / predicted N/A, true applicable / predicted applicable и отдельный missing. N/A accuracy — точность применимости, не точность всего значения.
- Scale MAE только для двух целых шкальных значений; critical TP/FP/FN/TN и precision/recall с `null` при пустом знаменателе.
- Исходные номера evidence и точное соответствие непустых цитат исходной реплике. Проверка текста не доказывает семантическую достаточность доказательства.
- Mean, median и p95 latency; p95 — nearest rank. Число повторов, сохранённые validation failures, неизвестные значения для старых попыток, usage и покрытие стоимости.
- Дельты provider credits по завершённым запускам. При конкурентном запуске это окно счётчика ключа для всего запуска; стоимость не распределяется выдуманно между моделями. Посторонняя активность того же ключа может влиять на дельту. Конвертация только с подтверждённым тарифом; при неизвестной стоимости — `null`. Резерв, usage и реальное изменение счётчика не смешиваются.

В accuracy попадают только парные случаи с действующим консенсусом; покрытие/число пар и размеченных случаев показаны рядом. Оценённый с ошибкой случай считается ошибкой по всем размеченным критериям. Ещё не запущенные случаи не выдаются за нулевую точность. Для ранжирования моделей нужны достаточные независимые эталоны и одинаковое покрытие.

## Безопасные команды сейчас: без платных вызовов

```sh

.venv/bin/python -m backend.app.batch_cli label-templates --out-dir data/my-human-labels
```

Имена выходных файлов/директорий должны быть новыми: реальные разметки и планы не перезаписываются молча. Импорт/разметка не вызывают AI. Создание плана не вызывает даже внешние GET: используется локальный ранее проверенный каталог. Обновить только каталог отдельным read-only GET при необходимости:

```sh
.venv/bin/python -m backend.app.batch_cli catalog --out data/multiai-models.json
```

## Завершённый preflight — архив параметров

План: `data/stage3-preflight-final.json`. Входы:

- RU `p1-ru-002`: уточнения, беспокойство клиента, безопасный следующий шаг.
- KZ `cqa-synthetic-kz-codeswitch-v1`: явно собственный RU/KZ code-switching.
- EN `p1-en-014`: идентификация и защищённые сведения.

Каждый — на `gpt-6.1-sol` и `gemini-3.8-flash`: **6 оценок**, ожидается **12 HTTP generations**, верхняя граница **24** с двумя попытками и двумя стадиями. Не следует называть это шестью HTTP-запросами.

Подтверждённый пользователем тариф 20 ₽ за миллион кредитов; сохранённый курс на 2026-11-07 — 82.1386 ₽/USD. Консервативный резерв: **1,154,200 кредитов = 23.084 ₽ ≈ $0.28104**. Лимит запуска $0.50 был одобрен и использован один раз. Это предварительная оценка по снимку каталога, не счёт и не обещание фактического списания. Перед этим запуском общий счётчик составлял 5 старых smoke-запросов; для полного верхнего предела нужен общий request limit как минимум 29.

Параметры закреплены в плане: concurrency=1, timeout=90 секунд, attempts≤2, backoff≤30 секунд, deadline=3300 секунд. Консервативная временная граница для этого preflight — 2400 секунд. Для 429 учитывается Retry-After (число секунд или HTTP date); если требуемое ожидание выше разрешённого, ранний повтор запрещён. Повторы не создают неограниченные циклы. Параметры исполнения нельзя незаметно изменить после согласования.

## Архив команды Stage 3 — НЕ повторять

Ниже историческая команда уже выполненного Stage 3. План id=6 завершён; команда больше не применима. Stage 3.5 изменил pipeline, поэтому нужен новый файл плана и отдельное разрешение на новый digest/count/USD cap. Архив:

```sh
ALLOW_PAID_CALLS=true MULTIAI_MAX_REQUESTS=29 \
  .venv/bin/python -m backend.app.batch_cli run data/stage3-preflight-final.json \
  --approved --evaluations 6 --limit-usd 0.50
```

CLI связывает разрешение только с digest этого плана внутри процесса; `.env` не разблокируется. API также требует `ALLOW_PAID_CALLS=true`, точный `MULTIAI_BATCH_APPROVED_PLAN`, `approved=true`, совпадающие count/budget/digest. План одноразовый. Подмена файла, транскрипта, параметров, кода pipeline, моделей, тарифа или состава набора останавливает запуск до платного запроса.

Перед исполнением проверяются актуальный read-only каталог/тариф и доступное место в глобальном лимите; тариф изменился — нужен новый план. Каждый POST атомарно резервирует расход одновременно в глобальном и отдельном run-бюджете. Параллельные задачи не обходят лимит. Резерв после ошибки/таймаута не возвращается. При deadline результат остаётся честной ошибкой; неизвестное выставление счёта отмечается, а не заменяется нулём.

## 10 настоящих PROD-чатов за час

Сейчас PROD отсутствует и не обрабатывается; файла результатов нет. После получения настоящего набора импортируйте его обычным существующим API, сохранив исходные IDs. Для планирования требуется **ровно 10** записей dataset=PROD и только `agent chat`.

```sh
.venv/bin/python -m backend.app.batch_cli prod \
  --model gpt-6.1-sol --concurrency 2 --timeout 90 --attempts 2 \
  --deadline 3300 --limit-usd 0.50 --out data/prod-plan.json
```

Это только план; модель и бюджет выбирает команда после benchmark. Для отсутствующих 10 входов команда корректно блокируется. При указанных параметрах временная верхняя оценка — 2010 секунд; deadline оставляет 5 минут до часа. С concurrency=1 при таком timeout/retry план может не уложиться и не допускается к исполнению. Реальное время/доступность шлюза не гарантируются; deadline создаёт error для незавершённых ID и сохраняет все 10 записей.

После отдельного разрешения исполнение того PROD-плана:

```sh
# Только после одобрения плана, model_id, 10 оценок, верхнего числа HTTP и USD cap.
# MULTIAI_MAX_REQUESTS должен вмещать текущее число + верхний предел этого плана.
ALLOW_PAID_CALLS=true .venv/bin/python -m backend.app.batch_cli run data/prod-plan.json \
  --approved --evaluations 10 --limit-usd 0.50
```

Runner использует ровно результаты этого запуска, только Official v1 и одну выбранную модель. Перед атомарной записью `results/prod/results.json` вызывается существующий строгий валидатор: 10 исходных IDs, все 8 критериев/типы/шкалы, evidence, score, critical_flag и корректные error-записи. Внутренние цитаты/метки/контексты не меняют официальный JSON 1.0. Невалидный документ не публикуется и не записывается вместо корректного файла. Дополнительная независимая проверка остаётся прежней:

```sh
.venv/bin/python -m backend.app.cli validate-export results/prod/results.json data/prod.json --dataset PROD
```
