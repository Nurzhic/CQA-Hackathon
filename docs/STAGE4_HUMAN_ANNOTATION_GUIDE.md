# Stage 4 — руководство по независимой человеческой разметке

**Обновление Stage 5:** для быстрого процесса используйте Benchmark → Human Fast Review → Expert A/B. Весь раунд из 18 случаев сохраняется атомарно; незавершённое — локально. Bulk Consensus и старый consensus API теперь требуют полных A и B по 18 случаев. [Пошаговые действия и ограничения](../output/STAGE5_ACCURACY_READINESS.md#9-точные-действия-пользователя).

Цель: два человека независимо размечают 18 исходных диалогов по Official v1, затем явно согласуют итог. Ответы GPT/Gemini не являются эталоном. На этом этапе не запускать AI и не обрабатывать PROD.

## 1. Организация работы двух людей

Назначьте эксперта A и эксперта B с разными именами. Оба должны понимать язык размечаемого диалога, включая казахский и RU/KZ. Обсуждать конкретные оценки можно только после полного завершения обоих раундов (по 18 случаев).

Используйте разные профили браузера, лучше разные компьютеры. Ведите список назначений: кто заполняет A, кто B, когда оба завершили версию. До окончания A/B не открывайте AI-карточки в «Диалогах», отчёты Stage 3/3.6 с модельными значениями, чужой раунд, экспорт чужой разметки или экран коллеги. Имеющиеся AI-результаты хранятся отдельно и в формы не подставляются.

**Авторизации в MVP нет.** Сервер проверяет разные имена A/B, но не удостоверяет личности. Переключение раунда и прямые API истории/согласования технически доступны любому пользователю. Сводка прогресса не содержит чужих значений/обоснований, форма A получает только A, форма B — только B; это защита обычного рабочего потока, не контроль доступа. Отдельные профили и договорённость команды обязательны. Если нужна гарантированная изоляция, потребуется отдельная авторизация/роли или организационно раздельные среды; сейчас такая гарантия не заявляется.

## 2. Как открыть Benchmark

Из корня проекта:

```sh
.venv/bin/uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
npm run dev --prefix frontend
```

Откройте **http://127.0.0.1:5173/#benchmark** — прямая ссылка сразу показывает Benchmark, без экрана с AI-оценками. При готовой production-сборке используйте **http://127.0.0.1:8000/#benchmark**. Если уже находитесь внутри приложения, нажмите «Benchmark» слева. Используйте один и тот же адрес/профиль для возвращения к локальным черновикам.

Нажмите **«Загрузить»**. Это читает локальные данные, не вызывает AI. Набор уже подготовлен; повторная подготовка не нужна. Должны появиться:

- `multilingual-v1`, 18 случаев: 6 RU, 6 KZ, 6 EN;
- 17 синтетических DEV организаторов и один явно отмеченный «СОБСТВЕННЫЙ» RU/KZ случай команды;
- счётчики A / B / consensus, каждый со знаменателем 18;
- при отсутствии эталонов — `unlabeled`, accuracy «—».

Кнопки dry-run и PROD относятся к планированию будущих запусков. Для разметки их не нажимать. «Проверить подключение» в настройках тоже не требуется.

## 3. Как заполнить A

1. **До выбора диалога** в верхнем поле «Рабочий раунд» выберите «Независимый A». Сначала раунд обязателен: это не даёт эксперту B случайно открыть A по умолчанию.
2. Выберите исходный ID из набора. Прочитайте весь оригинальный транскрипт, включая клиента, бота и систему, роли и timestamps.
3. Справа прочитайте описание каждого критерия, его вес, шкалу и условие N/A. Используется только Official v1.
4. Введите настоящее имя/согласованный идентификатор эксперта A.
5. Явно выберите значение **каждого из восьми критериев**. «Не размечено» — незавершённая работа, а не null.
6. Для каждого напишите своё обоснование и номера исходных реплик. Для пропуска действия укажите участок, где оно ожидалось.
7. При N/A заполните отдельную причину: какое именно условие неприменимости выполнено.
8. Если данных недостаточно для уверенного вывода, отметьте неопределённость и объясните её. Это не даёт права выбирать запрещённый N/A; например contact остаётся boolean.
9. Нажмите **«Сохранить человеческую версию»**. Это проверяет полноту и сохраняет новую неизменяемую серверную запись. Исправление — ещё одна версия, прежняя не удаляется.
10. Повторите для всех 18 случаев. До завершения не смотрите B и модельные ответы.

## 4. Как заполнить B

Эксперт B использует свой профиль браузера и выбирает **«Независимый B» до открытия первого диалога**. Затем выполняет те же шаги, формулируя собственные значения, rationale и evidence без чтения A.

Не копируйте A даже если кажется, что «и так всё ясно». Не просите AI заполнить форму, rationale, JSON-шаблон или спорные критерии. Один человек с двумя разными именами не образует независимые раунды.

Обычные формы A/B не содержат чужой разметки. После выбора «Согласование» ответы обоих становятся доступны только когда сохранены оба независимых раунда для всех 18 случаев; не переключайтесь туда раньше своей независимой работы.

## 5. Черновики: как прерваться и вернуться

Форма автоматически сохраняет **локальный черновик** в localStorage этого браузера. Смотрите сообщение «Черновик сохранён в этом браузере; это не эталон».

Чтобы продолжить: откройте тот же адрес в том же профиле, «Benchmark» → «Загрузить» → свой раунд → тот же ID. Незавершённые поля восстановятся. Пока не нажата серверная кнопка сохранения, счётчик A/B не растёт; черновик не участвует в accuracy.

Черновики разделены по раунду, ID, manifest/transcript/checklist hash, текущей серверной версии и A/B IDs для consensus. Если исходный контекст, серверная версия или ссылки consensus изменились, старый черновик автоматически не применяется. Локальное хранилище не зашифровано, не является резервной копией и не переносится между профилями/адресами. Очистка браузера его удалит. Если показано сообщение об ошибке localStorage, не закрывайте незавершённую форму: скопируйте свою работу в отдельный локальный файл и сохраните после заполнения всех критериев.

«Удалить локальный черновик» удаляет только черновик текущего случая/раунда, не серверную историю. После удаления заново выберите диалог для загрузки серверной версии. Не работайте двум людям в одном профиле: разные слоты localStorage не являются авторизацией.

## 6. Значения Official v1 и N/A

| criterion_id | Допустимые значения | Вес |
| --- | --- | --- |
| contact | true / false | 10 |
| discovery | true / false / null | 15 |
| identification | true / false / null | 20 |
| consultation | 0 / 5 / 10 / 15 / 20 / null | 20 |
| empathy | true / false | 15 |
| dialogue | 0 / 4 / 7 / 10 | 15 |
| closure | true / false / null | 5 |
| critical | true / false | 0 |

N/A означает **реальную неприменимость**, не «не знаю» и не «забыл заполнить». Условия из действующего Official v1:

- discovery: для ответа хватало исходных сведений, включая сообщения боту;
- identification: запрос не требовал идентификации, например общий вопрос о тарифах;
- consultation: чат закончился до формулировки запроса клиентом;
- closure: чат оборвался до возможности завершения.

Нельзя использовать null у contact, empathy, dialogue или critical. Для N/A обязательны rationale, na_reason и evidence, показывающие условие неприменимости. Применимость и значение должны быть обоснованы человеком; ответы AI не решают спор. Веса, шкалы и скоринг вручную не менять. Critical не обнуляет итоговый балл.

## 7. Evidence: исходные номера

Реплики нумеруются **с 1**, подряд по всему оригинальному транскрипту. Клиент, бот, система и оператор входят в общую нумерацию. Не перенумеровывайте только сообщения оператора и не переводите исходные цитаты.

В поле укажите целые номера через запятую: например `1, 4, 6` — это пример синтаксиса, не эталон какого-либо диалога. Каждый номер должен существовать в данном транскрипте. Пустое поле, 0, отрицательные, дробные и повторные номера не принимаются. Не исправляйте весь набор на +1 наугад: заново сопоставьте каждый номер с видимой репликой.

Evidence должно поддерживать именно ваш вывод. Наличие реплики с таким номером и буквальное совпадение текста не доказывают корректность оценки. Для нарушения последовательности полезны несколько реплик до/после действия. Для отсутствующего действия выберите реплику/участок, где действие ожидалось, и объясните пропуск. Не добавляйте несуществующие реплики и события за пределами чата.

## 8. Consensus: только после A и B

1. Когда оба человека сохранили полные независимые раунды по всем 18 случаям, откройте «Согласование» для того же ID. Если второго раунда нет, сравнение ещё не раскрывается и итог сохранить нельзя.
2. Прочитайте исходный диалог заново. Для каждого критерия можно раскрыть A/B: значения, rationale, evidence, N/A и uncertainty. Расхождения раскрываются автоматически.
3. Выберите итоговые **восемь значений**, человеческие обоснования и evidence. Ничего не заполняется из AI; формы не выбирают «более уверенную» модель.
4. Для **каждого расхождения** заполните «Причина решения по criterion_id». Расхождением считаются не только значения, но и evidence, rationale, N/A reason и uncertainty. Даже одинаковые значения могут требовать согласования разных объяснений.
5. Напишите общую причину согласования и укажите имя человека, фиксирующего совместное решение. Это может быть один из двух экспертов после обсуждения; автоматического консенсуса нет.
6. Сохраните. Итог закрепляет точные последние A/B IDs, контекст входов/чек-листа и причины решений. Изменение A или B делает предыдущий итог устаревшим до нового явного consensus.
7. Если спор не решён, не сохраняйте искусственный consensus. Оставьте кейс на согласовании; при необходимости запросите разъяснение организаторов/ответственного за регламент. Не объявляйте новое правило «официальным» и не берите ответ модели вместо решения людей.

Для JSON-импорта дополнительное поле consensus: `criterion_decisions`, словарь criterion_id → человеческая причина. `based_on` содержит актуальные `[A_id,B_id]`; `decision_reason` — общую причину. Независимые A/B не должны содержать эти ссылки/решения. Шаблоны намеренно содержат UNLABELED и не принимаются как эталон до ручного заполнения. Импорт выполняется атомарно; не используйте его для «сохранения» неполных черновиков.

## 9. Шесть спорных ситуаций: что проверять

Ниже вопросы для людей, **не готовые эталонные ответы и не новые правила организаторов**. Ориентир — описание текущего Official v1 в форме. Неоднозначность фиксируйте в rationale/решении.

### Клиент отказался от идентификации; защищённых действий не было

Проверьте identification: требовалась ли персональная проверка для фактически выполненной части запроса или обсуждалась только общая инструкция/безопасный следующий шаг? Отделите первоначальное желание проверить счёт от согласованного продолжения без проверки. Сам отказ клиента не доказывает ни автоматический провал оператора, ни автоматический N/A. Если требуемая проверка не подтверждена — правило говорит «Нет»; если запрос не требовал её — допускается N/A. Граница изменения объёма запроса может быть неоднозначной: согласуйте мотивировку и при необходимости уточните регламент. Также проверьте consultation, не раскрывались ли сведения (critical), и empathy.

### Следующий шаг предложен, но исходная проблема не решена

Проверьте consultation: Official v1 допускает максимальную ступень за закрытие существенных вопросов **или корректный следующий шаг**. Поэтому отсутствие немедленного решения само по себе не означает низкий балл. Проверьте конкретность, корректность и полноту шага, все вопросы клиента, оставшиеся существенные/второстепенные пробелы. Различайте ступени 20/15/10/5/0 по описанию в форме, не по уровню симпатии. Без регламентной базы нельзя придумывать срок/обязательный процесс эскалации. Evidence должно показывать вопросы и предложенный ответ. Дополнительно смотрите discovery и dialogue.

### Оператор попрощался, но не подвёл итог

Проверьте closure: `(итог ИЛИ предложение дальнейшей помощи) И прощание`. Отсутствие итога не означает провал, если есть предложение помощи и прощание. Одного прощания недостаточно. Отдельно проверьте, был ли чат оборван до возможности закрытия — это другая ситуация, для которой разрешён N/A. Сошлитесь на участок завершения.

### Сведения о счёте раскрыты до идентификации

Проверьте порядок: какие данные раскрыты, являются ли они конфиденциальными, есть ли предшествующее подтверждение личности, включая системные события. Identification и critical могут одновременно отражать одно нарушение: это не взаимозаменяемые критерии. Не выводите критичность лишь из слова «счёт», но и не предполагайте невидимую проверку. Critical ограничен тремя перечисленными в Official v1 классами; не расширяйте его своими правилами. Итоговый score критическим флагом не обнуляется.

### Клиент сообщил необходимые сведения ещё боту

Проверьте discovery по всей переписке до оператора. Если для ответа хватало информации с самого начала, предусмотрен N/A. Не требуйте повторного вопроса ради самого вопроса и не игнорируйте сведения боту. Если существенные детали отсутствовали, проверьте, уточнил ли их оператор до ответа. Полноту исходных сведений объясните evidence; близкие трактовки обсудите в consensus.

### RU/KZ code-switching

Проверьте contact по первому ответу и языковому контексту клиента, consultation по смыслу решения, empathy по реакции на конкретную проблему, dialogue по понятности и closure по совокупности действий. Не ставьте оценку по одному знакомому казахскому слову и не считайте само переключение языка нарушением. Сохраняйте казахские символы и исходные номера; не переводите цитаты автоматически. При недостаточной языковой компетенции нужен другой независимый человек, не AI-перевод эталона. Правила о допустимом языке нельзя придумывать сверх текущего чек-листа.

## 10. Как проверить завершение всех 18 случаев

В Benchmark → «Загрузить» проверьте **A 18/18, B 18/18, consensus 18/18** и статус `labeled`. Раскройте сводку статусов: ни один ID не должен оставаться `unlabeled` или `needs_adjudication`. Считаются актуальные версии данного manifest/checklist/transcript, а не количество исторических записей.

Фиксированный состав: 6 RU, 6 KZ, 6 EN; calibration 9, holdout 9. Holdout размечается людьми, но не используется для подбора AI-промптов. Не меняйте его после просмотра результатов моделей и не переносите туда удобные случаи.

Для офлайн отчёта без генерации:

```sh
.venv/bin/python -m backend.app.batch_cli report
```

54 актуальные записи (18 A + 18 B + 18 consensus) — ориентир полного первого прохода; при исправлениях физически записей может быть больше. Главный критерий — 18 действующих согласований, закрепляющих актуальные A/B.

Даже после разметки 18 случаев accuracy полного набора ещё нет, если моделей на нём не оценивали. Проверяйте `paired_labeled_cases`, выбранный pipeline и знаменатели: существующие парные ответы покрывают только три preflight-случая. Accuracy считается по значениям критериев, не по final_score; ошибка модели учитывается отдельно от отсутствия ещё не запущенного случая.

## 11. Перед следующим платным benchmark

Два человека сначала завершают и фиксируют независимые версии/consensus. Затем команда проверяет достаточность регламентов для спорных пунктов и замораживает эталоны. Проверки старых модельных результатов против новых меток выполняются офлайн на том же pipeline.

Для новых генераций потребуются **новый план с актуальным pipeline hash**, идентичный набор для обеих моделей, подтверждённые тарифы/лимиты, timeout/retry/request bounds и отдельное разрешение пользователя на число оценок и общий бюджет с retry. Старые планы №6/7 завершены и не переиспользуются. Stage 4 этого разрешения не даёт; `.env` оставлять с выключенным платным режимом. PROD — отдельный этап и отдельный набор.
